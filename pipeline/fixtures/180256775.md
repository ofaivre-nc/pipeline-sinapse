### RG-NOTE-OPTIMISTIC.LOCKING

**Règle RG-NOTE-OPTIMISTIC.LOCKING concernant l'optimistic locking**

Pour éviter les conflits de modification concurrente, le système utilise le mécanisme d'optimistic locking via le champ technique `version`.

Lors d'une modification (PUT/notes/{id}), le système :

1. Vérifie que le champ `version` fourni dans le DTO correspond à la version en base
2. Si les versions diffèrent → conflit détecté
3. Si OK → on procède à l’opération

**Implémentation API** :

- Modification

  - PUT/notes/{id} requiert le champ `version` dans le DTO `NotePut`
  - HTTP 409 Conflict avec code `NOTE-OPT-001` (modification concurrente, la note modifiée n’est pas la dernière version) si conflit détecté
  - Le nouveau `version` est retourné dans le DTO `NoteDetail` en réponse

### RG-NOTE-CREATION

**Règle RG-NOTE-CREATION concernant la création d'une note**

Lors de la création d'une note (POST /notes), le système enregistre les données fournies par l'utilisateur.

**Étapes** :

- Vérifie que la personne à laquelle la note est associée existe toujours en base (voir **RG-NOTE-ASSOCATION.PERSONNE**)

  - Si elle n’existe pas → conflit détecté
  - Sinon, vérifie que le type de note de la note existe toujours en base et que l’usager est autorisé à utiliser ce type de notes (voir **RG-NOTE-TYPENOTE **)

    - Si elle n’existe pas ou utilisateur non autorisé → conflit détecté
    - <mark style="background:#f8e6a0">Sinon, vérifie que les documents associés à la note existent toujours en base (voir </mark>**<mark style="background:#f8e6a0">RG-NOTE-ASSOCATION.DOCUMENTS</mark>**<mark style="background:#f8e6a0">)</mark>

      - <mark style="background:#f8e6a0">Si l’un des documents n’existe pas → conflit détecté</mark>
      - Sinon 

        - la note est crée.

**Création de la note ** avec :

**Champs renseignés par l'utilisateur** (DTO `NoteCreate`) :

- `idPersonne` (obligatoire) : uuid de la personne
- `idTypeNote` (obligatoire) : uuid du type de note
- `note` (obligatoire) : contenu de la note (max 3000 caractères)
- `exercice` (optionnel) : exercice comptable (format AAAA)
- `listeIdDocument`<mark style="background:#f8e6a0"> (optionnel) : liste d'uuid de documents</mark>

**Champs générés automatiquement par le système** :

- `id` : uuid technique
- `version` : 1 (optimistic lock initial)
- `idAuteurCreation` : ID (COMPTE.USER.id) de l'utilisateur connecté
- `dateCreation` : date/heure actuelle ([<u>Date (format long)</u>](https://sinapse-gie-nc.atlassian.net/wiki/spaces/SINAPSE/pages/8618004))
- `auteurModification` : ID (COMPTE.USER.id)  de l'utilisateur connecté (= auteurCreation pour V0)
- `dateModification` : date/heure actuelle (= dateCreation pour V0)

**Implémentation API** :

- POST /notes retourne HTTP 201 Created + Header `Location: /notes/{id}` + DTO `NoteDetail`

### RG-NOTE-MODIFICATION

**Règle RG-NOTE-MODIFICATION concernant la modification d'une note **

Lors de la modification d'une note (PUT/notes/{id}), le système met à jour la note concernée.

**Étapes** :

- Vérifie que l’utilisateur connecté est autorisé à modifier la note (voir **RG-NOTE-AUTEUR-AUTORISE-CREATION-MODIFICATION**)

  - S’il s’agit de personnes différentes → conflit détecté
  - Sinon, vérifie que le type de note de la note existe toujours en base et que l’usager est autorisé à utiliser ce type de notes (voir **RG-NOTE-TYPENOTE **)

    - Si elle n’existe pas ou utilisateur non autorisé → conflit détecté
    - Sinon, on vérifie que le champ `version` fourni dans le DTO correspond à la version en base (voir **RG-NOTE-OPTIMISTIC.LOCKING**)

      - Si les versions diffèrent → conflit détecté 
      - Sinon,  

        - la note est modifiée.

**Mise à jour de la note ** avec :

- **Champs identiques** (conservés) : `id`, `idPersonne`, `auteurCreation`, `dateCreation`
- **Champs incrémentés** : `version` = `version` + 1
- **Champs modifiés** : ceux fournis dans le DTO `NotePUT`(`idTypeNote`, `note`, `exercice`, `listeIdDocument`)
- **Champs système mis à jour** :

  - `idAuteurModification` = ID (COMPTE.USER.id) de l'utilisateur connecté

- PUT/notes/{id} retourne HTTP 200 OK + DTO `NoteDetail` (nouvelle version)
- HTTP 404 Not Found si la note n'existe pas

### RG-NOTE-RECHERCHE

**Règle RG-NOTE-RECHERCHE concernant la recherche de notes **

Le système ne liste que les notes qui répondent aux critères suivants :

  -  à la personne consultée (filtre `idPersonne`) si la recherche est via [CU-NOTE-CONSULTER](CU-NOTE-CONSULTER.md) 

**Critère 2 : Type de note autorisé**

  - Types associés à l’onglet affiché (filtre `onglet`) . Cela consiste à vérifier que` TypeNoteDetail.listeOnglet`contient les valeurs suivantes 

    - quand on ouvre la vue à partir d’une personne (fonctionnement nominal [CU-NOTE-CONSULTER](CU-NOTE-CONSULTER.md) ), la valeur `onglet`=vide car on affiche ici toutes les notes (sans limitation liée à l’onglet)

    - <mark style="background:#fedec8">quand on ouvre la vue à partir de la vue PCOL de la personne (fonctionnement variante 3.c), la valeur </mark>`onglet`=<mark style="background:#fedec8">"</mark>Procédures collectives<mark style="background:#fedec8">" </mark>

    - <mark style="background:#fedec8">quand on ouvre la vue à partir de la vue redressement de la personne (fonctionnement variante 3.e), la valeur </mark>`onglet`=<mark style="background:#fedec8">"</mark>Redressements<mark style="background:#fedec8">" </mark>

**Critère 3 : filtres appliqués dans l’IHM**

**Implémentation API** :

  - `onglet`: optionnel pour [CU-NOTE-RECHERCHER](CU-NOTE-RECHERCHER.md)et [CU-NOTE-CONSULTER](CU-NOTE-CONSULTER.md) , obligatoire dans les autres cas

- HTTP 403 Forbidden si l'utilisateur n'a pas accès à la personne.

### RG-NOTE-TYPENOTE-ONGLETS.AFFICHAGE

**Règle RG-NOTE-TYPENOTE-ONGLETS.AFFICHAGE concernant les onglets d'affichage (listeOnglet)**

Le champ `listeOnglet` est **optionnel **à la création et indique dans quel(s) onglet(s)/vue(s) les notes de ce type seront affichées.

**Valeurs possibles** : {Recouvrement, Procédures collectives, Travailleurs indépendants , Employeurs, Redressements, Réclamations}

### RG-NOTE-TYPENOTE-HABILITATIONS.REQUISES

**<mark style="background:#fedec8">Règle RG-NOTE-TYPENOTE-HABILITATIONS.REQUISES concernant les habilitations requises (listeHabilitation)</mark>**

Le champ `listeHabilitation` est **optionnel** et indique les habilitations nécessaires pour voir les notes de ce type.

Lors de la création/modification d’un type de note, on affiche l’ensemble des habilitations pouvant être utilisées pour limiter l’accès à un type de note donné.

- Appel [GET /habilitations](https://sinapse-gie-nc.atlassian.net/wiki/spaces/SINAPSE/pages/120160257)
- correspond à `HabilitationReponse.nom`
- Tri: ordre alphabétique croissant sur  `HabilitationReponse.nom`  

**Fonctionnement** :

- Si `listeHabilitation` est vide → Tous les utilisateurs peuvent voir les notes de ce type
- Si `listeHabilitation` contient 1 habilitation → L'utilisateur doit disposer de cette habilitation
- Si `listeHabilitation` contient N habilitations → L'utilisateur doit disposer **d'au moins une** de ces habilitations (OU logique)

**Exemple** :

- `listeHabilitation` = ["HAB-NOTE-GERER", "HAB-ADMIN"] → L'utilisateur avec HAB-NOTE-GERER **OU** HAB-ADMIN pourra voir les notes

**Implémentation API** :

- POST /types-note et PUT/types-note/{idTypeNote} acceptent `listeHabilitation` (optionnel)
- HTTP 400 Bad Request si `listeHabilitation` contient des valeurs invalides (habilitations non reconnues)
- Le filtrage côté consultation (GET /notes) applique automatiquement ce critère

### RG-NOTE-TYPENOTE-FILTRE.HABILITATIONS

**<mark style="background:#fedec8">Règle RG-NOTE-TYPENOTE-FILTRE.HABILITATIONS: Filtrage automatique sur habilitations utilisateur</mark>**

**Contexte** : Lors de l'appel GET /types-note avec l’option `habilitationFilter`=true, le backend doit filtrer automatiquement selon les habilitations de l'utilisateur connecté.

**Règle** :

- Le système retourne uniquement les types de note pour lesquels l'utilisateur dispose d'au moins une habilitation listée dans NOTE.TYPENOTE.listeHabilitation
- Si `listeHabilitation` est vide → le type est accessible à tous les utilisateurs
- Ce filtrage est **automatique**, que le filtre `onglet` soit fourni ou non, sous condition que `habilitationFilter`=true

**Exemple** :

- Utilisateur connecté : habilitations = [HAB-ADMIN, HAB-NOTE-GERER]
- Type A : listeHabilitation = [HAB-NOTE-GERER] → ✅ Visible
- Type B : listeHabilitation = [HAB-COMPTA] → ❌ Masqué
- Type C : listeHabilitation = [] (vide) → ✅ Visible (accessible à tous)

**Impact sécurité** :

- Empêche un utilisateur de créer/modifier une note avec un type pour lequel il n'a pas l'habilitation
- Cohérence IHM ↔ API : la liste déroulante ne propose que les types autorisés

### RG-NOTE-TYPENOTE-RECHERCHE-LIMITATION.ONGLET.HABILITATIONS

**Règle RG-NOTE-TYPENOTE-RECHERCHE-LIMITATION.ONGLET.HABILITATIONS concernant les types de note sélectionnables sur un onglet donné et selon les habilitations de l’utilisateur connecté.**

Dans le contexte d’affichage de notes dont le type est  limité à un onglet et/ou à des habilitations, le système doit afficher l’ensemble des valeurs de NOTE.TYPENOTE.typeNote correspondant à des types de note respectant les 2 contraintes suivantes:

- qui sont affichables dans cet onglet (l’onglet à partir duquel on visualise les notes est listé dans NOTE.TYPENOTE.listeOnglet)
- <mark style="background:#fedec8">pour lequel l’utilisateur a l’habilitation requise (l’utilisateur dispose d’une habilitation listée dans NOTE.TYPENOTE.listeHabilitation)</mark>

Cela est obtenu à partir de l’appel API [GET /types-note?onglet={onglet_actuel}&habilitationFilter=true](https://sinapse-gie-nc.atlassian.net/wiki/spaces/SINAPSE/pages/180289558) (NB: pas de paramètre `onglet` dans le cas de l’appel pour l’assistant de recherche de note, [CU-NOTE-RECHERCHER](CU-NOTE-RECHERCHER.md)ou depuis la consultation des notes d’un dossier [CU-NOTE-CONSULTER](CU-NOTE-CONSULTER.md) )

La liste sera triée par ordre alphabétique croissant.<br>Affichage : ``typeNote`` (libellé), Valeur : ``idTypeNote`` (uuid)

### RG-NOTE-TYPENOTE-RECHERCHE

**Règle RG-NOTE-TYPENOTE-RECHERCHE concernant la recherche de types de notes **

Le système liste les types de notes crées en base et potentiellement filtrées selon les filtres suivants: 

**Critère : filtres appliqués dans l’IHM**

- Si filtre modifié : `typeNote`, `onglet`,  `habilitation`

**Implémentation API** :

- GET /types-note avec filtres :

  - `typeNote`, `onglet`, `habilitation`: optionnel
  - Le recherche sur le filtre `typeNote` respecte la règle générique [RG-RECH-8 (recherche_texte_contient)](https://sinapse-gie-nc.atlassian.net/wiki/spaces/SINAPSE/pages/28803126). 
  - Option habilitationFilter = false
- tri par défaut : `?sort=typeNote` (ordre alphabétique croisant).
